# SAR Dispatch Flow — Claude Code Context

## ⚠️ Session Rules — Read Before Every Session

1. **Read this file AND run `git log --oneline -3`** before any code changes.
2. **Branch check:** Run `git branch --show-current` as a SEPARATE command immediately before `git add`. If result is `main`, STOP. Create a branch first.
3. **PR before build — always:** branch → commit → push → PR → Bill reviews + merges → THEN `bash build-*.sh` from a **freshly-pulled** main. Never self-merge. **`git pull --ff-only origin main` FIRST** — merging on GitHub does not move the local checkout, and `build-*.sh` deploys whatever `HEAD` is on disk, so building straight after a merge silently redeploys the *previous* version (near-miss 2026-07-25: local main sat 5 commits behind after #618/#619 merged; a build would have re-shipped 1.11.9). Confirm `cat VERSION` shows the bump you expect before building. **`build-dev.sh` and `build-sccssar-dev.sh` are deploy steps, not test runners.** Do NOT run them to validate your own in-progress changes — that pushes un-reviewed code to a real Cloud Run service. Local validation for your own changes = `python3 -m pytest -q backend/`. The only legitimate mid-task build is a pre-flight check that an *already-merged* predecessor PR is deployed, and only when the task spec explicitly asks for it. The moment you start editing files for the current task, the build script is off-limits until the PR merges.
4. **Do not revert Locked Design Decisions** without quoting the entry and getting explicit confirmation from Bill. Each row carries its own enforceable rule + failure mode; a handful of rows link out to [docs/design-decisions.md](docs/design-decisions.md) for longer root-cause history (that file is gitignored, local-only, and covers only the rows that link to it — it is NOT a complete rationale index).
5. **Server-side post-processing in `main.py` is intentional** — each `re.sub` has a documented failure mode. Do not remove thinking the prompt is "good enough."
6. **Verify CLI flags exist before documenting them** (`gcloud`, `docker`, etc.) — use `--help` first. Invalid flags silently break builds.
7. **`terraform apply` is required for any env var add/remove.** Build scripts don't pick up Terraform changes. Secret destroy order: remove from `main.tf` → `apply` → THEN destroy. **APPEND new `env` blocks to the END of the container's list — never insert mid-list.** Cloud Run `env` is an ORDERED LIST to Terraform, so inserting renumbers every block after it and the plan renders as a wall of renames (`~ name = "PROJECT_ID" -> "EVERBRIDGE_CALLER_ID"`). The net result is correct and nothing is destroyed — which is the problem: the diff is unreviewable, and a real mistake hides inside it. Measured 2026-09-04 on the 5-var Everbridge migration: **6 additions + 7 phantom renames** before, **6 additions + 0 renames** after moving the blocks to the end (PR #800). **Read the plan before every apply and expect `N added, 0 renames, 0 destroy`** — anything else means stop. Env var ORDER is not semantic to Cloud Run, so appending costs nothing.
8. **Check footer SHA vs HEAD before debugging — and verify a CODE MARKER, not just the version string.** Never assume the deployed build matches HEAD. **A matching footer does NOT prove the image is right.** `build-*.sh` reads `GIT_SHA` (line ~35) and `VERSION` (line ~40) into shell variables at script start, but `docker build` snapshots the build context ~40 lines later — so any git operation in the working tree between those two moments yields a **mislabeled Frankenstein image**: correct version args, wrong code. Bit us 2026-07-25 during the #616 live test — `/version` read `1.11.9 / 861cc7d` and matched HEAD *exactly*, while the served `frontend/index.html` was byte-identical to a different branch and the backend lacked the very gate under test. The dispatch returned 200 instead of 422 and ~an hour went into debugging a feature that had never been deployed. **The check that actually works** is to grep the served asset for a string unique to the change:
   ```bash
   curl -s https://<service-url>/ | grep -c stale_locality   # 0 = the build is lying
   ```
   Do this before debugging ANY "the code is deployed but not working" symptom. See Rule #16 for the other half.

   **Better than a marker: hash the whole served asset.** A marker taken from a diff's `+`
   lines is not necessarily new — on the 1.11.64 roll `git diff` showed `600 Tradan Dr.` as
   added, but `Tradan` occurs 3x in *both* versions, so `grep -c Tradan` would have returned
   3 and read as a **PASS on a build that never happened**. A whole-file hash needs no marker
   and cannot be fooled that way. **It requires exactly TWO normalizations**, because
   `backend/Dockerfile` rewrites two attributes at build time — `data-client_id` (line 44,
   #808) and `data-env-label` (line 54):

   ```bash
   URL=https://<service-url>
   curl -sS "$URL/" \
     | sed -e 's|data-client_id="[^"]*"|data-client_id="YOUR_OAUTH_CLIENT_ID.apps.googleusercontent.com"|' \
           -e 's|data-env-label="[^"]*"|data-env-label=""|' \
     | shasum -a 256
   git show HEAD:frontend/index.html | shasum -a 256      # must match
   ```

   **Normalizing only `data-client_id` FAILS on a correct personal-dev deploy** — that was
   the recipe merged in #817 and it was wrong. The two build scripts are asymmetric:
   `build-dev.sh:108` passes `--build-arg ENV_LABEL` (the SANDBOX banner) while
   `build-sccssar-dev.sh` does not, so on sccssar-dev the line-54 `sed` rewrites `""` to `""`
   and is a no-op — which is why the one-normalization version looked correct when written.
   Measured live 2026-09-05 against `1.11.65 / 3983ff6`, both envs served, `HEAD` =
   `bef5b827…`: personal-dev one-norm `844e5d64…` **FAIL** / two-norm `bef5b827…` PASS;
   sccssar-dev passed either way. **A verification step that fails on a correct deploy is
   worse than none** — it trains you to ignore the check, which is the state this Rule exists
   to prevent. Adding a third build-time `sed` to the Dockerfile means adding a third `-e`
   here; there is no test pinning this, so the Dockerfile is the source of truth — read it.

   **`curl -s` hides a failed request and `shasum` of an empty body is a fixed value**
   (`e3b0c442…`). Use `curl -sS`, and refuse to hash a body under ~1 KB — otherwise every
   variant "matches" and the check silently passes against nothing.
   **Verify by the check that CAN fail on this release — and every release class retires the previous class's check.** Measured across four consecutive rolls on 2026-09-06/07: a *frontend* change is proven by the served `index.html` sha256 above; a *backend-only* change (1.11.67) makes that hash a CONSTANT, so hash `/app/main.py` out of the digest Cloud Run **serves** instead (read it off the REVISION — `docker push` printed a different digest on every build so far); a *dependency-only* change (1.11.68) makes the `main.py` hash a constant too, so `docker run --rm --entrypoint pip <served-digest> freeze` is the check; a *build-context* change like `.dockerignore` (1.11.69) is proven by `ls /app` inside the image, not by any hash. Before building, name the check that can fail, take its **pre-build negative control from the outgoing image**, and refuse to call a matching constant a PASS. A pin that cannot fail is the same as no pin.
9. **Everbridge/Slack work builds to `bash build-dev.sh` (personal dev) only.** Never `build-sccssar-dev.sh` for EB/Slack — that environment has real dispatchers who can be paged.
10. **Empirically verify third-party API assumptions before writing integration code.** Use Swagger or a spike script to confirm endpoint path, HTTP verb, body shape, and auth BEFORE coding. Prior sessions lost hours to wrong assumptions (DELETE-that-doesn't-exist, `groupId` vs `groupIds`, outer envelope vs inner body). Applies to: Everbridge, Slack, CalTopo, D4H, Google Maps. Skip only if the exact endpoint shape is already confirmed in shipped code.
11. **End every session with (a) a copy-pasteable next-session continuation prompt, (b) a MEMORY.md update, AND (c) a `docs/release-notes.md` update if a new version deployed.** The continuation prompt names the immediate next action, open backlog items, and any active gotcha. The MEMORY.md update adds one "Recent sessions" row (date + one-line summary + links to any new feedback/topic files created this session); bump the "Current state" header date + bullets if material state changed (new PRs merged, mode flag flipped, integration went live, etc.). **Release notes (c):** if one or more new VERSION numbers were DEPLOYED this session (a `bash build-*.sh` ran and the live footer version changed — not merely a merged VERSION bump), add a newest-first, dispatcher-facing `docs/release-notes.md` entry for the deployed version(s), matching the file's house style (`## YYYY-MM-DD — <headline>` + `**Version:** \`<version> · EB: <mode> · Slack: <mode>\`` + plain-language "what changed for you"). Internal-only changes (no dispatcher-visible effect) get a one-line mention under the current version rather than their own entry. **(d) Draft the dispatcher announcement email** whenever (c) fires AND the release carries dispatcher-facing new features or a significant bug fix. Draft it WITHOUT being asked — Bill decides whether to send, and the bar for drafting is lower than the bar for sending. **Whether it SENDS is decided by the call to action, not by severity (Bill, 2026-08-25):** ask *does this give the dispatcher something NEW to do?* 1.11.63 fixed a bug that had destroyed the only correct location on a real callout and was still not sent, because the dispatcher's takeaway reduced to "do not typo the LKP", which has been true since 1.0.0. When the CTA collapses to standing advice, say so on handover instead of presenting the draft as ready. Style rules (subject carries the features, or the fix on a fix-only release; change-type label per item; features before fixes; credit the origin; one rule per item; one light joke; no reassurance closer) live in the `feedback-dispatcher-release-emails` memory. Also assess whether CLAUDE.md needs an update — most sessions don't; only trigger when a Locked Decision or Session Rule was discovered or refined (e.g., a new failure mode + guardrail was added, an empirical truth was validated, a Rule needs clarification). Skip only if Bill explicitly says no need.
12. **Proactively surface untested failure modes before Bill hits them.** When something is built but not live-tested, call it out. Sequence test plans: solo-doable first, read-only first, multi-person last.
13. **Doc-vs-code sweep before architectural prose refresh.** When refreshing prose that describes a component (D4H, EB, rate limits, Overpass mirrors, etc.), grep BOTH the doc AND the code/MEMORY for that component, reconcile, then edit. The PR #506–#513 cycle (May 2026) showed that editing the words on the page without sweeping leaves Phase-N-1 facts in place (D4H "stub" surviving long after Phase 2 live, 3-mirror Overpass list surviving past maps.mail.ru removal, etc.). `backend/test_doc_parity.py` pins a starter set of brittle facts; for prose claims the sweep is manual but mechanical.
14. **Chain `checkout → add → commit` into ONE Bash call — the harness auto-pulls `origin/main` between calls.** Observed 4+ times (late-May 2026): a `git checkout -b foo` followed by separate `git add`/`git commit` calls can land the commit on local `main` instead of `foo`, because the harness silently resets HEAD mid-flight; remote `foo` ends up empty. **Prevention:** `git checkout <branch> && git add <files> && git commit -m "…"` as a single command. **Symptom:** `[main <sha>]` in commit output, or `git branch --show-current` returning `main` when you expected a feature branch. **Recovery:** `git checkout <branch> && git cherry-pick <shas> && git push --force-with-lease origin <branch> && git checkout main && git reset --hard origin/main`.
15. **After every real-world callout — and every live end-to-end dispatch test — run the `dispatch-after-action` skill** ([.claude/skills/dispatch-after-action/SKILL.md](.claude/skills/dispatch-after-action/SKILL.md)). It reads the incident's Cloud Run logs first, then walks a guided interview across intake/OCR, staging, Slack, D4H, CalTopo, process, and feature asks, and writes a report to gitignored `research/after-action/`. Lessons learned from real callouts are the highest-value input this project gets and the easiest to lose; don't reconstruct the review ad hoc.
16. **The working tree is FROZEN while a build runs.** From the moment `bash build-*.sh` starts until it prints `Deploy complete`, do NOT run `git checkout`, `switch`, `stash`, `pull`, `reset`, or branch-create in the main repo. The Docker context is snapshotted mid-script (Rule #8), and `COPY backend/*.py` + `COPY frontend/` take whatever is on disk at that instant — so a concurrent checkout silently substitutes another branch's code into the image while the version args still say `main`. **Violated 2026-07-25:** a `git checkout --detach origin/fix/staging-distance-sanity`, run to execute a second PR's test suite while a build was in flight, put pre-#616 code into an image labelled `1.11.9 / 861cc7d` and invalidated the live test. **To work on another branch during a build, use a worktree OUTSIDE the repo directory** (`git worktree add /tmp/wt-foo <branch>`) — not `.claude/worktrees/`, which sits inside the build context. Corollary: **announce before touching the tree** when a build may be running, and prefer read-only commands (`git show <ref>:<path>`, `git diff <a>..<b>`) over checkout for inspecting other branches — they never touch the working tree.

## Behavioral Defaults

These apply on top of (not in place of) the base Claude Code defaults around minimal abstraction and no speculative code. Source: external reviewer suggestions (Melanie, 2026-05-25) + Bill's stated complaints about adjacent fixes, hard-to-grok diffs, and acting before surfacing alternatives.

1. **Smallest diff that achieves the goal.** No reformatting, renaming, or refactoring of code outside the task scope. Match existing style even if you'd write it differently.
2. **Surface alternatives before implementing** when more than one reasonable approach exists, or when your interpretation of the request is uncertain. Don't silently pick — name the options, recommend one, let Bill redirect.
3. **No unsolicited cleanup.** If you notice unrelated dead code, stale comments, or lint issues, mention them; don't fix them in this PR. Exception: orphans YOUR change created (unused imports, dead helpers introduced by an earlier draft).
4. **No duplicate explanation.** If a name, type, or adjacent code already conveys the WHAT, don't add a comment that repeats it. The same rule applies to `.md` files — no filler, no restating what the code or another doc already says.
5. **Scope balloon → flag, don't expand.** If a task grows past its original framing mid-flight, stop and surface the new scope rather than silently bundling it in. The "one logical change per PR" rule in [Git/PR Workflow](#git--pr-workflow) is downstream of this.

## Failure-mode Discipline

Answer these six questions before opening a PR that touches handlers calling external systems (`/send-notification`, `/poll-incident`, `/close-incident-polling`, `backend/everbridge.py`, `backend/slack.py`, `backend/d4h.py`, `backend/caltopo.py`). Source: every one of the 28 findings in Melanie's 2026-05-25 batch-2 review (PRs #515–#524) traces back to one of these six. Backend handler code defaults to writing the happy path; the failure paths need this rubric.

1. **What is the point of no return?** Once it crosses (EB notification fires, Slack message posts), what does the rollback or journal look like? Every side-effect ID (`everbridge_event_id`, `notification_id`, `slack_channel_id`, `welcome_ts`, `caltopo_ts`, `tally_ts`) must be persisted to Firestore the moment it's obtained — not at the final `.set()`. Pattern: PR-C (#517).
2. **What happens between line N and line N+1?** Network dies, Cloud Run preempts, an exception fires in the next call. Does the handler crash and orphan, or does it `try/except + log + continue` and reach the closure write? Every call after the point of no return is best-effort. Pattern: PR-A (#515).
3. **What does this return value mean?** `bool` / `Optional[...]` returns from `end_notification`, `mark_member_attending`, and similar must be captured and surfaced — not discarded as bare expression statements. Pinned by `backend/test_discarded_return_values.py`. Pattern: PRs D (#518) + E (#523).
4. **Can this run twice concurrently?** Double-click within ~1 second produces two requests; the rate limiter does NOT catch the 2nd (it catches the 6th). Atomic `.create()` of a tombstone document before any side effect is the only sufficient guard. Pattern: PR-B (#516).
5. **Is the failure mode typed?** Client errors (4xx, non-retriable) and server errors (5xx, transient) must route to different Cloud Tasks responses (200/400 = drop; 502 = retry). A blanket `except` that 502s everything pollutes the retry budget with un-retriable failures. Pattern: PR-D (#518).
6. **Are the two legs of a 2-leg API symmetric?** If GET-404 returns `False` but PUT-404 raises, the caller sees idempotent behavior on one path and a crash on the other. Same class: empty-string vs `None` vs missing-key on inputs, case-sensitivity on capability tags (`"UAS"` vs `"uas"`), and falsy-fallthrough where an empty list is a valid result. Pattern: PRs E (#523) + F (#524).

Backend handler PRs should run a self-review pass against this rubric before `gh pr create` — see [Git/PR Workflow](#git--pr-workflow).

## Architecture

```
Browser (plain HTML/JS)  →  Google Sign-In (GSI)
    → Cloud Run backend (Python FastAPI, gen2)
        → Vertex AI Gemini 2.5 Flash  (Pass 1: OCR; Pass 2: staging+Koester)
        → Nominatim                   (OSM geocoding — LKP address → lat/lng)
        → Overpass API                (OSM POI lookup, 3 mirror fallbacks, 1200m)
        → Google Maps Geocoding API   (spelling-correction fallback)
        → Firestore                   (rate limiting + incident polling state)
        → Everbridge REST API         (group notification + polling)
        → Slack API                   (private incident channels + #active-incidents)
        → Google Drive API            (dispatcher OAuth, drive.file scope)
        → CalTopo Team API            (HMAC-SHA256 signed incident maps)
```

Two-pass Gemini per submission: Pass 1 extracts LKP → geocode + Overpass POI fetch → Pass 2 formats staging + Koester with real coords and candidates injected as INTERNAL data.

## Critical Privacy & Security

1. Form images **never stored** — raw bytes in-memory only, garbage-collected after response.
2. Intake form data **session-scoped** — lives only in the browser and in-flight API response.
3. **No PII in logs** — only latency, finish_reason, error type. No names, DOBs, addresses.
4. Auth on every endpoint — valid Google ID token from allowlist required.
5. All credentials in Secret Manager / terraform.tfvars — never in source.

Security assessments saved to `research/security-assessment-YYYY-MM-DD.md` (gitignored). Re-review triggers in `SECURITY.md`. Check triggers before any new endpoint, auth, or file-parsing work.

## Git / PR Workflow

Every change: **branch → commit → PR → Bill merges → `bash build-*.sh`**. Bill reviews and merges all PRs; never self-merge (including Dependabot).

```bash
git branch --show-current              # Verify branch BEFORE git add
git checkout -b fix/description        # Branch off main
# ... make changes ...
git add <specific files>               # Never git add -A
git commit -m "$(cat <<'EOF'
fix: short imperative description (≤70 chars)

Why this change was needed. Reference the failure mode that prompted it.

Co-Authored-By: Claude Sonnet 4.6 <noreply@anthropic.com>
EOF
)"
git push -u origin fix/description
gh pr create --title "fix: description" --body "$(cat <<'EOF'
## Summary
- bullet

## Test plan
- [ ] item

Closes #NNN
EOF
)"
```

**Don't write closing keywords (`close`/`closes`/`closed`/`fix`/`fixes`/`fixed`/`resolve`/`resolves`/`resolved`) adjacent to `#N` in a PR body unless you actually want GitHub to close issue N on merge — even inside a conditional sentence.** GitHub's parser is regex-only with no context awareness; "If clean, close #519" closes #519 on merge. Safe rewrites: "we can close issue 519" (no `#`), "the conditions to close issue [#519](url) are…" (no keyword adjacent to `#N`), or "mark [#519](url) resolved" (`mark` is not a keyword). The `Closes #NNN` line in the template above is the canonical intentional use — the warning is about INCIDENTAL adjacency in test plans, conditionals, and prose. PR #531 (2026-05-28) hit this — auto-closed #519 before observation-window data existed.

**One logical change per PR.** If you find a second issue, note it and file separately after merge.

**Self-review pass before `gh pr create` (backend-handler PRs).** When the diff touches `backend/main.py` handlers (`/send-notification`, `/poll-incident`, `/close-incident-polling`, `/dispatch-status`, `/incident-status`) or `backend/{everbridge,slack,d4h,caltopo}.py`, dispatch the `feature-dev:code-reviewer` agent against the diff with the [Failure-mode Discipline](#failure-mode-discipline) six-question rubric as the prompt before opening the PR. The reviewer agent runs in parallel, takes ~1–2 minutes, and on the 2026-05-25 batch-2 retrospective would have caught Clusters A/B/C/D-H1 on first pass — the highest-severity findings (orphan-after-EB, double-dispatch race, side-effect-before-persistence, Cloud Tasks retry-pollution). Skip for pure-text helpers, frontend, Terraform, and docs.

## Build Verification

**Before any build:** `git pull --ff-only origin main` FIRST, confirm `cat VERSION`, then verify a CODE MARKER rather than the footer (Rules #8 + #16). **On a backend-only release `frontend/index.html` is unchanged, so Rule #8's sha256 check matches whether or not the build ran** — it is a constant, not a test. Verify the backend instead: resolve the digest Cloud Run is actually serving (`gcloud run revisions describe <rev> --format='value(spec.containers[0].image)'`, which is NOT the digest `docker push` printed), pull that, and hash the module against `git show HEAD:backend/<module>.py`. `backend/Dockerfile` does `COPY backend/*.py .`, so the path inside the image is **`/app/main.py`**, not `/app/backend/main.py`. No build-time `sed` touches `backend/`, so this comparison needs no normalization. Take a pre-build negative control: the check must MATCH the live version's source and DIFFER from HEAD's before you trust it after.

**A code marker taken from a diff's `+` lines is NOT necessarily new — validate it against BOTH versions and take a pre-build negative control.** On the 1.11.64 roll, `git diff` showed `600 Tradan Dr.` as an added line, but `Tradan` occurs 3x in *both* 1.11.63 and HEAD (the change was the house number, and surrounding context had moved). A post-build `grep -c Tradan` would have returned 3 and read as a **PASS on a build that had not happened**. What works: diff the two versions' files directly, pick a string that is provably `0` in the old and `>0` in the new, curl the live service BEFORE the build to confirm it reads `0`, and prefer the **full-file sha256 check in Session Rule #8**, which needs no marker at all and is what actually confirmed this deploy.

**The whole-file sha256 check and its TWO required normalizations now live in Session Rule #8**, so they survive the next handover rewrite of this section. Do not restate them here.
