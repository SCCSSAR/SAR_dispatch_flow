## Release History

**Milestone numbering convention** (rationalized 2026-04-26):

Going forward, the milestone string in the footer + this table is the **GitHub
Milestone label**, drawn from the repository's GitHub milestone labels.
Each milestone is a themed feature epic with a number + name (e.g.
`1.6 Twin Peaks` for PDF intake, `1.7 Accountant` for SCCSSAR-dev migration,
`1.8 Slacker` for Everbridge + Slack integration).

From v1.8.0 onward (PR #561), each milestone also contains numbered
**VERSION rows** (1.8.0, 1.8.1, 1.9.0, ...) sourced from the repo-root `VERSION`
file. Per-VERSION rows live UNDER the milestone row and summarize the
constituent PRs in one dense paragraph each. Per-PR rows are still discouraged
— batch dispatcher-visible PRs into per-VERSION rows instead (that's how the
`1.5z*` letter tail accumulated 30+ rows below; do NOT recreate that pattern).
Bump procedure: each PR that ships a change bumps `VERSION`; merge conflicts on
that file serialize concurrent PRs.

The build scripts (`build-dev.sh`, `build-sccssar-dev.sh`) bake both the
milestone string AND the semantic version into the image at build time via
`--build-arg PHASE="1.8 Slacker" --build-arg VERSION="$(cat VERSION)"`. The
footer reads them from `/version` and renders `<version> · EB: <mode> · Slack:
<mode>` (phase + SHA in hover tooltip). Bump the `PHASE=` value in both build
scripts when starting a new milestone; bump `VERSION` in each PR that ships a
change.

Historical rows below (Phase 1.5*, Phase 1.1, etc.) are kept as a per-PR
ledger from before this convention — read them as a low-level changelog of
how the 1.5 milestone grew. Do NOT delete them; do NOT add similar per-PR rows
under newer milestones.
